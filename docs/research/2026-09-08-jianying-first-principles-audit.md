# 剪映模块可用性与完整性评估

结论：**NOT VERIFIED**。

待验证的主张是：用户可以把当前 cut-list 可靠地交付到剪映，找到并打开工程，继续修改
视频、字幕和音轨，保存重开，并从剪映生成符合编辑意图的成片，同时保留正确输入来源。
当前实现没有达到这一定义。它是有价值的实验性草稿生成与文件交接原型，尚不能作为
完整、经过原生客户端验收的剪映集成模块交付。

评估日期：2026-09-08。代码基线：`1b65b03bbf49ed84d91eaa81d0450a253591c3b6`。
本轮读取当前源码与公开参考实现，重新执行现有专项测试，并在临时合成项目中做反例。
没有修改产品代码或实际剪映库，也没有安装客户端。这是本会话自审，不是独立第三方验收。

## 1 从用户结果定义完成

文件是交付载体，剪映才是读取工程并呈现编辑结果的程序。因此至少需要逐层满足：

| 层次 | 用户需要的结果 | 当前证据与结论 |
|---|---|---|
| 编辑决策 | 源区间、轨道、文本与主音轨被保留 | 大部分已编码到 JSON，并有合成测试 |
| 文件包 | 素材能打包，路径和文件完整性可检查 | 有实现；基本打包/复制流程验证通过 |
| 语义有效 | 原生轨道、片段、素材引用和时间互相一致 | 校验不完整；反例已穿过验证及安装 |
| 输入一致 | 草稿对应正确的清单版本和素材版本 | 存在已复现的时间窗口问题 |
| 原生可发现 | 剪映主页能找到这个草稿 | 没有客户端证据；复制目录不等于登记成功 |
| 原生可编辑 | 打开无丢素材，字幕与片段可修改 | 没有客户端证据 |
| 原生可保存 | 修改后保存、退出、重开仍保留 | 没有客户端证据 |
| 原生可生成 | 用剪映导出并检查画面、声音与时长 | 没有自动调用实现，也没有人工原生验收 |
| 版本兼容 | 具体 Mac/Windows 剪映版本有通过记录 | 没有已验收的客户端版本矩阵 |

不要求一开始支持所有特效，也不要求读回加密草稿或将人工修改同步回 CLI。
但找到工程、打开、可编辑、保存重开和导出，是“剪完还能继续调”的基本完成条件。

## 3 已复现的问题

### P1 导出清单与清单哈希不是同一份快照

位置：[export/jianying.py](../../src/interview_edit/export/jianying.py)，`export_jianying`。

函数先使用传入的内存 document 生成草稿，再读取磁盘 cut-list 的哈希。若用户或另一个
进程在这两个动作之间保存清单，草稿仍是旧内容，manifest 却会记录新文件的哈希。
结尾只和这个较晚取得的哈希比较，无法发现错配。

| 同一小型案例 | 基线 | 模拟保存新清单后 |
|---|---:|---:|
| 生成的草稿时长 | 800000 µs | 800000 µs |
| manifest 所对应磁盘清单的时长 | 800000 µs | 700000 µs |
| 导出是否返回成功 | 是 | 是 |
| manifest 哈希是否匹配当前清单文件 | 是 | 是，但内容对应错了版本 |

该反例在真正的 CLI 调用中，对 `DraftBuilder.build` 包装一个受控时序钩子，在生成内存
草稿后保存另一个合法 cut-list。产品源码未改动；该钩子模拟外部保存，不伪造导出结果。

修复要求：从同一份读取快照同时获得解析对象与字节哈希，或在入口证明传入 document
对应该文件；发布前再次比较这份起始快照。不能把末尾才拿到的文件哈希冒充生成依据。

### P1 素材校验后发生替换 可导出越界工程

位置：同一导出服务的初始 `validate_cutlist`、较晚的 `source_hashes` 和发布前检查。

当前先按旧索引校验素材，然后把后续读到的素材哈希当成新基线。若素材在初始校验后、
首次哈希前被外部进程替换，复制和末尾哈希都可能一致，但素材时长/内容已不同于索引。

临时测试把原片从 1.2 秒换成 0.4 秒，保留旧的 0.1–0.9 秒剪辑范围：

| 检查项 | 观察值 |
|---|---:|
| 索引声明的原片时长 | 1200000 µs |
| 实际打包的媒体时长 | 400000 µs |
| 草稿片段的源出点 | 900000 µs |
| 导出返回成功 | 是 |
| `verify_draft` 返回通过 | 是 |

这里用的是测试生成的媒体，模拟其他程序改动输入；并不是导出器主动修改了用户原片。
问题在于输入版本约束失效，实际包中的视频已短于草稿引用范围。

修复要求：让复制内容、媒体元数据与索引身份来自一致证据；发布前重新验证源版本，
并将起始哈希绑定到索引中已批准的输入。仅检查“复制前后哈希一样”不能补齐旧索引身份。

### P1 原生草稿缺少语义校验

位置：[export/jianying.py](../../src/interview_edit/export/jianying.py) 的 `_verify_draft`；
[安装器](../../src/interview_edit/export/jianying_install.py) 直接依赖该验证结果。

对有效导出包分别构造三个反例，并同步更新对应文件的大小与哈希，让文件完整性条件
仍然成立。每个包都通过 `verify_draft`，并被 `install_draft` 写入临时草稿库：

| 反例 | 验证结果 | 文件安装结果 |
|---|---|---|
| segment.material_id 指向不存在的素材 | 通过 | 成功 |
| 保留非零 duration，但 tracks 为空 | 通过 | 成功 |
| 片段 target_timerange.start 为 -100000 | 通过 | 成功 |

这并非说 SHA-256 校验失效。没有更新哈希的损坏文件会被既有检查拦住；反例证明的是
当前验证器不能识别“由生成器或工具产生、哈希自洽，但原生时间线无效”的产物。

应增加与 serializer 独立的语义检查：轨道与素材类型、全局 ID 唯一性、所有引用可解析、
整数非负时间、正时长、源范围和目标时长关系、轨道重叠规则、辅助素材引用、文本样式
区间及打包资源绑定。再以真实剪映创建的脱敏 fixture 验证，而不只检测自己生成的数据形状。

## 4 尚未证实的关键风险

### 草稿目录复制不保证客户端可发现

现有安装器刻意不修改 `root_meta_info.json`。临时空注册库中复制草稿后，目录存在，
`all_draft_store` 仍是空列表。这个结果只证明没有登记，不能单独证明某版本剪映一定
找不到，因为应用也可能扫描目录并补登记。

但 [video-shotcraft 的 Mac 安装实现](https://github.com/Vincentwei1021/video-shotcraft/blob/5f047c7cfe10d6616fe59160a750fcfaea510b2e/jianying-export/mac_draft.py)
[T1，公开实现与作者实测说明] 明确包括退出应用、备份注册表、插入 `all_draft_store`
记录以及失败回滚。这说明“完全不碰注册信息，重启就能出现”需要实机证明，不能作为通用前提。

不建议现在盲目复制其登记代码。应先观察目标版本是目录扫描、注册表还是原生导入，
采用相应机制，并测试已有项目保护、失败恢复和界面可见性。

### 平台与版本适配太薄

当前两端的主要分支是文件名和 `platform.os`；模板使用固定版本标记并清空设备信息。
这有隐私价值，但并不能证明所有版本都接受该组合。Mac 检测读取安装信息但不选择不同
草稿格式；Windows 版本字段为 null，也没有支持版本范围、已知不兼容版本或回归 fixture。

不能把参考项目对某个版本的成功记录转移成本项目的成功记录。也不能直接把清空设备 ID
判为错误：最小必需字段应由目标应用创建的样本和实际导入结果确认，而非自动采集用户设备信息。

### 实际调用剪映尚未实现

现有命令只有导出、检测和复制安装。安装结束后提示用户打开应用；没有启动并打开指定
草稿、确认编辑器加载、原生导出任务、导出成功检测或输出验证。因此“让剪映实际生成
视频”仍是未完成的产品步骤，不是再添加几个 JSON 字段就能证明的能力。

### 原生画面和声音保真尚无证据

字体、字幕背景、图层顺序、逐层淡入淡出、旋转素材、分数帧率和变速音频都需要客户端
样例验证。当前 alpha/volume 关键帧有相应字段，不等于它们在实际重叠图层中的效果已
被核验。CLI master 的响度处理没有应用到剪映工程，原生输出应另测响度与峰值。

本报告不把这些全部列为确定 bug，也不凭缺少实测就断言所有草稿无法打开。

### 长项目操作体验还不完整

默认便携模式复制完整原片和字体，并在取基线、复制校验、文件清单、发布前检查等环节
多次读取文件。空间预估、路径保护和失败清理已经具备，但导出/安装没有进度回调、分块
恢复或素材复用；中断会清掉自己的 staging，下一次重新开始。小型样片通过不能代表
几十 GB 项目的等待体验已经可用。这需要真实规模测试后设计，不能先编造耗时改善比例。

## 6 初始假设的结果

| 假设 | 结果 |
|---|---|
| 现有结构测试足以证明可用且完整 | 否定；反例能穿过校验/安装，原生流程也未测试 |
| 校验值能够把导出绑定到正确输入版本 | 否定其当前充分性；清单与媒体竞态均已复现 |
| 复制草稿目录即可使两端应用识别 | 证据不足；存在采用注册流程的公开 Mac 实现，当前无客户端观察 |
| 现有 cut-list/独立轨道设计可作为后续基础 | 保留；结构和复用方向合理，无需因此推倒重来 |

反面观点与回应：

- “模块标注实验性，因此这些都可以接受。”实验标记避免误导，但不消除输入错配和
  语义漏检；可以用于联调，不应作为用户可依赖的完成状态。
- “哈希能拦住修改，没必要再验证时间线。”哈希说明内容与清单一致，不能说明内容正确；
  serializer 自己写出的错误也会拥有正确哈希。
- “只要装好剪映，就能把状态改成完成。”安装只解除前置条件；发现、打开、修改、保存
  重开和导出仍需逐项观察。两个已复现输入问题也不会因安装应用自动消失。
- “应该直接换成成熟库。”可以减少手写协议，但上游也有版本与平台限制；仍需要本项目
  的适配、输入一致性、用户工程保护与原生验收。

## 7 建议修复顺序与完成条件

1. **先修正确性。** 清单快照绑定、索引/素材版本绑定、原生语义验证三个缺口应加失败
   回归用例后修复。阈值是上述反例全部被拒绝，且不写入正式导出/安装目录。
2. **建立最小原生验收。** 选定一个明确的 Mac 版本和一个明确的 Windows 版本；使用
   合成样片检验列表可见、无丢素材、字幕可改、片段可调、保存重开和原生导出。只有实际
   通过的版本进入支持列表，未知版本保持实验状态。
3. **按实测补交接机制。** 确定每个目标版本如何登记/导入草稿，并覆盖目录、缓存和
   注册信息的恢复流程。安装返回“文件已复制”和“应用已接受”应是不同的结果字段。
4. **补原生操作与输出检查。** 用户若要真正通过剪映生成最终视频，需要新增经过验证
   的打开/导出操作，或明确的人工交接流程；输出再用独立媒体检查验证时长、声音、画面。
5. **扩充质量与性能样本。** 先覆盖中英字幕、emoji、不同画幅、长素材、分数帧率、
   多机位/漂移和覆盖层淡入淡出，再决定是否扩大特效支持。逐项标明验证平台与版本。

建议保留 PR #2 的实验标签，不按“剪映模块完整可用”验收。当前代码可用于开发联调；
在正确性修复和原生小样通过前，不应依赖它交付重要项目。

## 8 证据与范围

反例脚本及原始 JSON 结果位于当前机器的 `/tmp/verify-this/jianying-audit/`，仅使用合成
素材，没有进入 Git。复现包括三种语义缺陷、一次清单保存竞态、一次素材替换竞态，以及
注册表未变化观察。每个反例以同一套真实导出/验证/安装函数运行，只有竞态注入点被包装。

本轮未修改代码、未弱化测试、未向 GitHub 发布评论。之前的 PRD 文件保持原样。
目前没有原生剪映客户端或真实项目样本，所以不能给出客户端打开成功率、两端视觉保真率
或性能提升百分比。
